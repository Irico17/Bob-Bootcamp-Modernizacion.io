Contenerización con Spec-Driven Development

Spec-Driven Development Plan → Agent → Ask K8s / OpenShift Podman

En lugar de pedirle a Bob un Dockerfile suelto, primero escribes una spec: qué debe cumplir la contenerización y cómo se comprueba. Bob implementa contra esa spec y la verificas criterio por criterio.

Laboratorio opcional: se le asignan solo ~10 min. Si el tiempo no alcanza, haz los pasos 1 a 3 y omite la verificación local con Podman.

1. ¿Qué es spec-driven development?

Es una forma de trabajar con agentes donde la spec (un documento versionado en el repo) es la fuente de verdad: las personas deciden el qué (requisitos y criterios de aceptación) y Bob se encarga del cómo. Si el resultado no encaja, se corrige la spec o la implementación, no se improvisa con prompts nuevos.

Prompts sueltosSpec-driven
RequisitosViven en el chat y en tu cabezaUn archivo spec.md con IDs (R1…R10)
“Terminado”Se ve bienCriterios de aceptación verificables (CA1…CA5)
CambiosOtro prompt, sin rastroSe edita la spec y se implementa solo la diferencia
RevisiónSubjetivaTabla de trazabilidad requisito → archivo → evidencia

Bob no necesita un workflow especial para esto: usas sus modos. Agent escribe y ejecuta, Plan razona y propone sin tocar código, y Ask es de solo lectura, ideal como revisor independiente. Referencia de la práctica: Spec-driven Development with IBM Bob.

4. Paso 1 · Escribir la spec Agent · 3 min

En modo Agent, pídele a Bob que cree el archivo de la spec. Aquí te damos una spec lista para ahorrar tiempo; léela y ajústala: decidir qué se exige es la parte que le corresponde a la persona, no al agente. 

Crea el archivo specs/contenerizacion/spec.md con el siguiente contenido exacto:

# Spec: contenerización de lab-api

## Contexto
App Java 17 (Maven). JAR ejecutable en target/app.jar. Servidor HTTP del JDK en el puerto 8080
(variable PORT). GET /health devuelve {"status":"UP"}.

## Objetivo
Construir una imagen de contenedor y desplegarla en Kubernetes / OpenShift de forma segura y reproducible.

## Fuera de alcance
Registro de imágenes, CI/CD, Helm/Kustomize, bases de datos.

## Requisitos
- R1  Dockerfile multi-stage: la imagen final no contiene Maven ni el JDK completo (solo JRE).
- R2  Imagen base oficial y slim (Temurin 17 JRE o UBI9 openjdk-17-runtime).
- R3  Se ejecuta como no-root y es compatible con el UID arbitrario de OpenShift (grupo 0 con permisos).
- R4  Expone el puerto 8080 y respeta la variable PORT.
- R5  Existe .dockerignore que excluye target/, .git/ y archivos de IDE.
- R6  Deployment de 1 réplica con readinessProbe y livenessProbe a GET /health en el puerto 8080.
- R7  securityContext: runAsNonRoot, allowPrivilegeEscalation: false, capabilities drop ALL, seccompProfile RuntimeDefault.
- R8  Requests y limits de CPU y memoria definidos.
- R9  Service ClusterIP y Route de OpenShift que exponen la app.
- R10 Sin secretos hardcodeados; labels consistentes app=lab-api.

## Criterios de aceptación
- CA1 El Dockerfile y el .dockerignore cumplen R1 a R5 (revisión estática).
- CA2 Los manifiestos en k8s/ cumplen R6 a R10 (revisión estática).
- CA3 "podman build -t lab-api:1.0 ." termina sin errores.
- CA4 Al correr la imagen, GET /health responde {"status":"UP"}.
- CA5 Cada requisito R1 a R10 se puede trazar a un archivo y una línea concreta.
Fíjate en dos detalles: cada requisito tiene un ID (para poder trazarlo) y hay una sección de fuera de alcance (para que Bob no invente Helm, CI/CD, etc.).

5. Paso 2 · Revisar la spec y planear Plan · 2 min

Cambia a modo Plan (selector de modo o /plan). Antes de implementar, pídele a Bob que cuestione la spec: una spec ambigua produce una implementación ambigua. 

Lee specs/contenerizacion/spec.md.
1. Señala ambigüedades, contradicciones o requisitos que no se puedan verificar.
2. Propón un plan de implementación y una lista de tareas ordenadas; cada tarea debe indicar
   qué requisitos (R#) cubre.
No generes código todavía.

Si Bob encuentra problemas reales, corrige la spec (no el plan) y vuelve a pedirlo. Cuando el plan te convenza, sigue.

6. Paso 3 · Implementar contra la spec Agent · 3 min

Vuelve a modo Agent e indícale que la spec manda:

Implementa la spec specs/contenerizacion/spec.md siguiendo el plan aprobado.
Genera: Dockerfile, .dockerignore, k8s/deployment.yaml, k8s/service.yaml y k8s/route.yaml.
En un comentario junto a cada decisión indica el requisito que cumple (por ejemplo "# R3").
No modifiques la spec ni el código de la aplicación.
Si algún requisito no es viable, detente y dímelo en lugar de improvisar.
Que Bob se detenga ante un requisito inviable es parte del método: el desacuerdo se resuelve en la spec, no con un parche silencioso.

7. Paso 4 · Verificar contra la spec Ask · 2 min

Cambia a modo Ask (solo lectura, /ask). Es un revisor independiente: no puede “arreglar” nada a escondidas. 

Actúa como revisor. Compara los archivos generados (Dockerfile, .dockerignore, k8s/*.yaml)
con specs/contenerizacion/spec.md.
Para cada requisito R1 a R10 y cada criterio CA1 y CA2, muestra una tabla:
ID | Archivo y línea que lo cumple | Estado (Cumple / Parcial / No cumple) | Evidencia.
Al final lista las brechas y propón si se corrigen en la implementación o en la spec.

Si hay brechas, vuelve a Agent para corregir solo lo que falta y repite la verificación. Ese ciclo spec → implementar → verificar es el corazón del método.

8. Verificación local opcional · criterios CA3 y CA4

Si hay tiempo, demuestra con hechos que se cumple la spec:

Sin contenedor (sanity check)

mvn -q -DskipTests package
java -jar target/app.jar
# otra terminal:
curl http://localhost:8080/health
curl "http://localhost:8080/fare?plan=CORPORATE&minutes=150&data=800&peak=true"
curl "http://localhost:8080/discount?customerId=C2&amount=200"

Podman (preferible)

podman build -t lab-api:1.0 .
podman run -d --name lab-api -p 8080:8080 lab-api:1.0
curl http://localhost:8080/health
podman logs lab-api
podman ps
podman stop lab-api && podman rm lab-api

Docker

docker build -t lab-api:1.0 .
docker run -d --name lab-api -p 8080:8080 lab-api:1.0
curl http://localhost:8080/health
docker stop lab-api && docker rm lab-api

Manifiestos con Podman

podman kube play k8s/deployment.yaml
podman pod ps
curl http://localhost:8080/health
podman kube down k8s/deployment.yaml
No uses podman run y kube play a la vez en el mismo puerto/nombre.

Cluster (opcional)

kubectl apply -f k8s/deployment.yaml -f k8s/service.yaml
kubectl get pods -w
kubectl port-forward svc/lab-api 8080:80
curl http://localhost:8080/health
# OpenShift: oc apply -f k8s/route.yaml && oc get route

9. Extra · Cambiar la spec opcional

Así se evoluciona un proyecto spec-driven: primero cambia el documento y luego se implementa solo la diferencia. Por ejemplo, para exigir que los tests del Lab 3 pasen antes de generar la imagen: 

Agrega a specs/contenerizacion/spec.md el requisito
"R11  El stage de build ejecuta mvn verify, de modo que la imagen solo se genera si todos los unit tests pasan"
y el criterio "CA6 Un test fallido hace fallar podman build".
Luego implementa únicamente el cambio necesario en el Dockerfile, citando R11, y actualiza la verificación.

10. Criterios de éxito

  • La spec existe en el repo, con requisitos con ID y criterios de aceptación
  • Bob generó Dockerfile, .dockerignore y k8s/*.yaml citando los requisitos
  • La tabla de trazabilidad (Paso 4) muestra R1 a R10 como “Cumple”, o las brechas están identificadas
  • (Si hubo tiempo) imagen local y /health → {"status":"UP"}
